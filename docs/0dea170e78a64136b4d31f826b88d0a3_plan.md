## 문제 및 배경
PostgreSQL에 저장된 단어에 오타가 있어도 현재 애플리케이션에서 수정할 수 없어 데이터베이스를 직접 조작해야 한다. 기존 단어 관리 화면과 디자인을 유지하면서, 선택한 단어 한 건을 안전하게 수정하는 기능이 필요하다.

## 명시적 요구사항
- 데이터베이스에 저장된 기존 단어를 애플리케이션에서 수정할 수 있어야 한다.
- 예문은 수정 대상에서 제외한다.
- 예문과 서버 관리 필드를 제외한 기존 사용자 입력 필드를 수정할 수 있어야 한다.
- 동일한 단어나 내용의 중복 저장을 허용한다.
- 관리자 계정이나 역할 체계를 새로 만들지 않는다.
- 동시성 제어, 수정 이력 및 되돌리기는 구현하지 않는다.
- 기존 색상, 레이아웃, 타이포그래피 등 시각 디자인을 변경하지 않는다.
- 기존 JavaScript/TypeScript, Next.js, React 및 PostgreSQL 구조를 유지한다.
- 필요한 최소 자동 테스트를 추가할 수 있다.
- 배포하거나 운영 데이터를 직접 변경하지 않는다.

## 목표
- 기존 단어의 현재 값을 확인하고 오타를 수정한다.
- 불변 레코드 ID로 대상 한 건만 갱신한다.
- 예문, ID, 타임스탬프 등 수정 불가 필드를 보존한다.
- 클라이언트와 서버에서 입력값을 검증한다.
- 저장 성공 결과가 화면과 이후 조회에 반영되도록 한다.
- 기존 조회, 등록 및 학습 흐름과 디자인을 보존한다.

## 비목표
- 예문 수정.
- 일괄 수정 또는 전역 찾아 바꾸기.
- 자동 맞춤법 교정이나 AI 추천.
- 신규 로그인, 관리자 계정 또는 역할 기반 권한 관리.
- 수정 이력, 감사 로그 또는 되돌리기.
- 낙관적 잠금, 버전 비교 또는 충돌 알림.
- 데이터 모델이나 디자인 시스템의 전면 개편.
- 운영 배포 또는 운영 데이터 직접 수정.

## 사용자 스토리
- 사용자는 등록된 단어의 오타를 발견했을 때 해당 항목을 열고 바로 수정하고 싶다.
- 사용자는 수정 화면에서 기존 값을 확인하고 필요한 필드만 고치고 싶다.
- 사용자는 저장 전에 편집을 취소할 수 있어야 한다.
- 사용자는 저장 실패 시 입력한 내용을 잃지 않고 재시도하고 싶다.

## 사용자 흐름
`기존 단어 선택 → 기존 액션 위치에서 수정 진입 → 현재 값이 채워진 폼 표시 → 값 변경 → 저장 또는 취소 → 성공 시 최신 데이터 표시`

저장 시 클라이언트 기본 검증 후 기존 Next.js 서버 경계를 호출한다. 서버는 레코드 ID, 허용 필드 및 입력값을 다시 검증하고 PostgreSQL의 대상 한 행만 갱신한다.

## 기능 요구사항
- 기존 단어 목록 또는 상세 화면에 기존 액션 패턴을 재사용한 수정 진입점을 제공한다.
- 편집 폼은 예문을 제외한 기존 사용자 입력 필드의 현재 값을 표시한다.
- 예문, ID, 생성일, 수정일 및 내부 상태는 편집할 수 없다.
- 수정 요청은 편집 가능한 필드의 전체 현재 값을 전송하며 서버가 명시적 allowlist로 DTO를 재구성한다.
- 변경 사항이 없으면 저장을 비활성화하거나 데이터 변경 없이 성공 처리한다.
- 저장 중 반복 제출을 방지하고 기존 UI 패턴으로 진행 상태를 표시한다.
- 동일한 내용의 다른 레코드가 있어도 저장을 허용한다.
- 성공 시 서버가 반환한 최신 값으로 화면 및 관련 캐시를 갱신한다.
- 취소 시 서버 요청이나 데이터 변경 없이 편집을 종료한다.
- 존재하지 않는 ID는 데이터 변경 없이 404 대응 오류로 처리한다.
- 검증 또는 서버 오류가 발생해도 편집 중인 값을 유지한다.

## 비기능 요구사항
- 기존 입력, 버튼, 모달 또는 편집 페이지 컴포넌트와 스타일을 재사용한다.
- 신규 색상, 레이아웃, 타이포그래피 또는 별도 디자인 체계를 추가하지 않는다.
- 키보드로 수정, 저장 및 취소할 수 있어야 하며 레이블과 오류가 보조기술에 전달되어야 한다.
- 브라우저가 PostgreSQL에 직접 접근하지 않는다.
- 모든 SQL은 파라미터 바인딩을 사용한다.
- 오류 응답에 SQL, 스택 추적, 접속 정보 등 내부 정보를 노출하지 않는다.
- 기존 조회, 등록 및 학습 계약의 하위 호환성을 유지한다.

## 엣지 케이스
- 필수값이 비었거나 공백만 입력된 경우.
- 허용 길이를 초과하거나 지원하지 않는 형식이 입력된 경우.
- 한글, 영문, 악센트 문자 등 유니코드가 입력된 경우.
- 동일한 단어나 내용이 이미 존재하는 경우: 허용한다.
- 저장 전에 대상 레코드가 삭제된 경우.
- 조작된 ID, 예문 또는 서버 관리 필드가 요청에 포함된 경우.
- 저장 중 네트워크 또는 서버 오류가 발생한 경우.
- 저장 버튼을 빠르게 반복 클릭한 경우.
- 두 저장이 동시에 발생한 경우: 별도 충돌 감지 없이 마지막으로 완료된 유효 저장을 유지한다.

## 가정 및 기본값
- 수정은 전역 문자열 치환이 아니라 불변 ID 기반 단일 레코드 편집이다.
- 정확한 수정 필드와 컬럼명은 구현 전 기존 생성 폼과 스키마를 조사해 확정한다. 사용자 입력 필드 중 예문만 제외하며 서버 관리 필드는 항상 제외한다.
- 편집 방식은 기존 프로젝트에 모달 패턴이 있으면 모달을 재사용하고, 없으면 기존 단어 화면 안의 편집 상태를 사용한다. 새 페이지나 스타일 체계는 만들지 않는다.
- 기존 접근 제어가 있으면 그대로 재사용한다. 접근 제어가 없다면 단독 사용자라는 현재 배포 경계를 유지하며 신규 인증이나 RBAC를 추가하지 않는다.
- 중복 금지 제약이 없다면 데이터베이스 마이그레이션은 만들지 않는다. 내용 기반 고유 제약이 실제로 저장을 막는 경우에만 최소 마이그레이션으로 해당 제약을 제거한다.
- 기존 테스트 도구가 없으면 Vitest, React Testing Library 및 jsdom을 우선하는 최소 구성을 추가하되, 실제 패키지 검사 결과 더 가까운 기존 관례가 있으면 그 관례를 따른다.
- 동시 저장은 마지막 유효 저장 우선 정책을 적용한다.

## 권고사항

- 단어 문자열이 아닌 불변 기본 키를 수정 식별자로 사용한다.
- 클라이언트 객체를 그대로 SQL에 전달하지 않고 서버 allowlist로 수정 DTO를 재구성한다.
- 데이터베이스 변경 전에 실제 고유 제약과 자연 키 의존 호출부를 확인한다.

## 검사 상태
현재 실행 정책이 워크스페이스 프로세스 생성을 차단하여 실제 소스, `context.md`, 스키마 및 패키지 구성을 읽지 못했다. PostgreSQL 계획에 필요한 `supabase-postgres-best-practices` 스킬 파일도 같은 정책으로 읽을 수 없었다. 따라서 아래는 확정된 제품 계약과 보수적 구현 기본값이며, T-01에서 실제 경로, 필드명 및 관례를 읽기 전용으로 확인해야 한다. 계획 단계에서는 소스를 수정하거나 검사를 통과했다고 주장하지 않는다.

## 현재 아키텍처
- JavaScript/TypeScript, Next.js, React, npm 및 PostgreSQL을 사용하는 기존 프로젝트다.
- 주요 디렉터리 경계는 `frontend`, `backend`, `docs`로 제시되었다.
- Project Context에는 별도 backend가 없다고 표시되어 있어 서버 mutation은 Next.js 서버 경계에 있을 가능성이 높다.
- Router 유형, 서버 mutation 방식, PostgreSQL 클라이언트, 단어 스키마, 캐시 및 테스트 도구는 T-01에서 확정한다.

## 제안 아키텍처
기존 모듈 경계를 보존하며 `단어 목록·상세 화면 → 기존 컴포넌트를 재사용한 편집 폼 → 기존 Next.js 서버 mutation/API → 공유 검증 → 단어 저장소 → PostgreSQL` 흐름을 추가한다. 별도 서비스, 브라우저 DB 연결, 신규 관리자 체계 또는 디자인 시스템은 도입하지 않는다.

## 모듈 경계 및 의존성
- UI: 수정 진입점, 기존 값 초기화, 폼 상태, 저장·취소 및 오류 표시.
- 도메인/검증: 수정 가능 필드, 예문 제외 규칙, 필수값, 공백, 길이 및 형식 검증.
- 서버 mutation/API: 요청 파싱, 필드 allowlist, 검증, 오류 매핑 및 캐시 갱신.
- 저장소: 불변 ID 기반 단일 레코드 조회 및 UPDATE.
- 데이터베이스: 기존 스키마 유지. 내용 기반 중복 금지 제약이 확인될 때만 조건부 마이그레이션.
- 의존 방향: UI → 서버 계약 → 도메인 검증 → 저장소 → PostgreSQL.

## API 및 서버 계약
기존 Route Handler, API route 또는 Server Action 관례를 우선한다. 해당 관례가 없으면 `PATCH /api/words/{id}` 형태의 Route Handler를 사용한다.
- 요청 경로의 ID와 예문을 제외한 편집 가능 사용자 필드의 전체 현재 값을 받는다.
- 요청 본문에 ID, 예문, 타임스탬프, 내부 상태 또는 알 수 없는 필드가 있으면 거부한다.
- 서버는 요청 객체를 그대로 저장소에 전달하지 않고 명시적 allowlist로 DTO를 재구성한다.
- 성공 시 갱신된 공개 단어 DTO를 반환한다.
- 기존 오류 계약이 있으면 재사용한다. 없으면 422 검증 오류, 404 미존재, 500 일반 내부 오류를 사용한다.
- 중복 내용은 오류로 취급하지 않는다.
- 동시성 토큰이나 409 충돌 계약은 추가하지 않는다.

## 데이터베이스 및 마이그레이션
- 기존 불변 기본 키를 UPDATE 조건으로 사용한다.
- 기존 PostgreSQL 쿼리 도구의 파라미터 바인딩으로 `UPDATE ... SET ... WHERE id = ... RETURNING ...`과 동등한 단일 문장을 사용한다.
- SET 절에는 조사로 확정된 편집 가능 컬럼만 명시하며 예문과 서버 관리 컬럼은 포함하지 않는다.
- 반환 행이 없으면 404로 매핑한다.
- 단일 UPDATE의 PostgreSQL 문장 단위 원자성을 사용하며 별도 트랜잭션이나 잠금은 추가하지 않는다.
- 버전 또는 잠금용 컬럼을 추가하지 않는다.
- 중복 사전 검사 쿼리를 수행하지 않는다.
- 내용 기반 고유 제약이 없다면 마이그레이션은 필요 없다.
- 내용 기반 고유 제약이 확인되면 자연 키 유일성에 의존하는 조회 및 연결 코드를 먼저 조사한 후 그 제약만 제거하는 최소 마이그레이션을 작성한다. 기본 키와 시스템 식별자의 유일성은 유지한다.
- 운영 데이터와 운영 스키마는 직접 변경하지 않는다.

## 프런트엔드 및 도메인 모델
- 기존 단어 목록 또는 상세 화면의 기존 액션 위치에 수정 진입점을 둔다.
- 기존 생성/관리 폼, 입력 컴포넌트, 버튼 variant, 간격 및 오류 표현을 재사용한다.
- 기존 모달 패턴이 있으면 모달을 사용하고, 없으면 현재 단어 화면 안에 편집 상태를 추가한다.
- 신규 색상, 레이아웃, 타이포그래피 또는 독자적인 스타일 파일을 추가하지 않는다.
- 편집 모델은 불변 ID와 예문을 제외한 사용자 입력 필드로 제한한다.
- 예문은 필요한 경우 읽기 전용으로 표시할 수 있지만 편집 컨트롤과 수정 DTO에는 포함하지 않는다.
- 성공 시 서버 응답으로 화면을 갱신하고 필요한 캐시만 재검증한다.
- 실패 시 폼을 닫지 않고 사용자의 입력을 보존한다.

## 인증 및 권한
- 단독 사용자 요구에 따라 신규 로그인, 관리자 계정 또는 역할 기반 권한 체계를 추가하지 않는다.
- 기존 세션이나 접근 제어가 있으면 수정 mutation에도 동일하게 적용한다.
- 기존 접근 제어가 없으면 현재 단독 사용자 배포 경계를 유지하며 이번 기능만을 위해 인증 체계를 신설하지 않는다.
- 요청 본문의 사용자 ID나 역할 값은 신뢰하지 않는다.

## 검증 및 오류 처리
- 예문, ID, 타임스탬프 및 알 수 없는 필드는 거부한다.
- 필수 문자열의 빈 값과 공백만 있는 값을 거부한다.
- 공백 정리, 최대 길이, 유니코드 및 형식 규칙은 기존 생성 규칙을 공유한다.
- 중복 여부는 검증 오류가 아니다.
- 수정 가능 필드가 하나도 없는 요청은 검증 오류로 처리한다.
- 변경 전후 값이 같으면 데이터 변경 없는 성공으로 처리하거나 UI에서 저장을 비활성화한다.
- 필드 오류는 UI가 해당 입력과 연결할 수 있는 안정적인 구조로 반환한다.
- 데이터베이스와 내부 예외 메시지는 사용자 응답에 포함하지 않는다.

## 보안 및 동시성
- 모든 SQL에 파라미터 바인딩을 적용한다.
- 서버 allowlist와 명시적인 SET 절로 mass-assignment 및 예문 변조를 방지한다.
- 기존 쿠키 인증이 있다면 현재 SameSite 및 CSRF 보호 관례를 재사용한다.
- 저장 중 버튼을 비활성화해 우발적 반복 제출을 방지한다.
- 버전 비교와 낙관적 잠금은 구현하지 않는다.
- 동시에 저장되면 마지막으로 완료된 유효 요청이 최종값이 된다.

## 호환성
- 기존 조회, 등록 및 학습 API와 공개 DTO를 깨뜨리지 않는 추가 변경으로 구현한다.
- 기존 URL과 탐색 흐름을 유지한다.
- 고유 제약을 제거해야 한다면 자연 키 유일성을 전제로 한 호출부를 먼저 수정한다.
- 예문 데이터의 형식과 저장 동작은 변경하지 않는다.

## 관찰 가능성
- 기존 로깅 체계가 있으면 수정 실패를 현재 구조에 맞춰 기록한다.
- 필요한 경우 레코드 ID, 결과 코드 및 지연 시간만 기록한다.
- 단어 본문, 예문, 세션 값 및 접속 정보는 로그에 기록하지 않는다.
- 수정 이력 저장소나 신규 외부 모니터링 플랫폼은 MVP에 포함하지 않는다.

## 테스트 전략

- 저장소 통합 테스트: 정상 UPDATE, 대상 한 건만 변경, 미존재 ID, 예문 보존 및 동일 내용 저장.
- API/서버 계약 테스트: 성공, 검증 오류, 404, 내부 오류 및 허용되지 않은 필드 거부.
- 컴포넌트 테스트: 현재 값 초기화, 예문 편집 불가, 취소, 변경 없음, 저장 중 비활성화, 실패 시 입력 유지 및 성공 후 최신 값 표시.
- 회귀 테스트: 기존 단어 조회, 등록 및 학습 흐름 유지.

## 아키텍처

기존 Next.js/React 모듈 경계를 유지한다. 데이터 흐름은 `단어 목록·상세 화면 → 기존 디자인 컴포넌트를 재사용한 편집 폼 → 기존 Next.js 서버 mutation/API → 공유 검증 → 단어 저장소 → PostgreSQL`이다. 수정은 불변 레코드 ID를 조건으로 한 파라미터화 단일 행 UPDATE로 수행하고, 예문과 서버 관리 필드는 서버 allowlist 및 명시적 SET 절에서 제외한다. 중복 내용은 허용하며 신규 관리자 RBAC, 동시성 토큰, 별도 백엔드 서비스 및 새 디자인 체계는 도입하지 않는다.
