# ChanVoca 다중 사용자 전환 계획

- 작성일: 2026-10-27
- 상세 실행·검증 계획 갱신일: 2026-10-27
- 상태: 승인 후 로컬 구현·핵심 검증 완료. 운영 배포·운영 DB 변경은 수행하지 않음. 실제 결과와 미검증 항목은 MULTI_USER_VERIFICATION.md 참조.
- 목표: 기존 개인 데이터를 보존하면서, 초대받은 사용자가 각자의 단어장·학습 기록·알림을 사용하는 구조로 전환한다.

## 1. 이번에 구현할 범위

기존 Next.js 프론트엔드, Fastify 백엔드, PostgreSQL, 작업 큐를 유지한다. 계정 수를 코드에 고정하지 않는다.

| 항목 | 계획 |
| --- | --- |
| 로그인 | 아이디 + 비밀번호 |
| 가입 | 운영자가 발급하는 일회용 초대 코드로 가입 |
| 계정별 데이터 | 단어장, Day 번호, 학습 진행·결과, 알림 설정, 푸시 구독 분리 |
| 본인 데이터 | 기존 `owner`의 사용자 ID를 본인 로그인 계정에 연결 |
| 인증 유지 | 서버에서 관리하는 인증 세션 + HttpOnly 쿠키 |
| 비밀번호 복구 | 초기에는 서버 운영 명령으로 재설정하고 해당 계정의 모든 인증 세션 무효화 |
| 사용량 제한 | 로그인·가입 요청 제한과 사용자별 일일 업로드 카드 수 제한 |

이번 범위에는 공개 회원가입, 소셜 로그인, 이메일 발송, 관리자 웹 화면, 단어장 공유, 결제, 사용자별 별도 DB를 포함하지 않는다. 초대 코드 전달은 운영자가 직접 한다.

## 2. 현재 구조에서 바꿀 지점

- `auth/auth.ts`, `auth/auth.routes.ts`: 공용 `APP_PASSWORD`와 사용자 식별자가 없는 서명 쿠키를 계정 인증으로 교체한다.
- `app.ts`: 세션 유효 여부만 확인하는 훅을 변경해 검증된 사용자 ID를 요청에 연결한다.
- `system/owner.ts`: 일반 API에서의 `getOwnerId()` 호출을 제거한다. 기존 owner 연결은 초기 설정 명령에서만 명시적으로 처리한다.
- `days`, `study`, `notifications`: 기존 사용자별 쿼리 조건에 로그인한 사용자 ID를 전달한다.
- `frontend/src/components/auth-gate.tsx`: 아이디 입력과 초대 가입을 추가한다.
- `frontend/src/components/study-app.tsx`: 현재 계정을 표시하고 계정별로 이어하기 저장 키를 구분한다.
- `frontend/src/components/notification-settings.tsx`, 푸시 worker: 계정 전환 시 기기 구독과 대기 알림이 다른 계정에 연결되지 않도록 변경한다.

카드는 `days`, 학습 시도는 `study_sessions`를 통해 소유권을 확인한다. 모든 하위 테이블에 중복으로 `user_id`를 추가하지 않는다.

## 3. DB와 기존 데이터 보존

기존 migration 파일은 수정하지 않고 후속 migration을 추가한다. 사용자 및 인증 정보의 책임은 `auth` 모듈로 정리하고 문서의 모듈 경계도 맞춘다.

| 테이블 | 용도와 주요 정보 |
| --- | --- |
| 기존 `users` | 사용자 ID와 표시 이름·시간대 유지 |
| 신규 `auth_credentials` | 사용자 ID, 정규화된 고유 로그인 ID, 비밀번호 해시 |
| 신규 `auth_sessions` | 세션 ID, 무작위 토큰의 해시, 사용자 ID, 생성·만료·무효화 시각 |
| 신규 `auth_invites` | 초대 코드 해시, 만료 시각, 사용·취소 시각 |
| 신규 `auth_rate_limits` | 재시작·다중 API 프로세스에서도 공유하는 요청 제한 카운터와 만료 시각 |
| 기존 `push_subscriptions` 확장 | 구독을 연결한 인증 세션 ID. 해당 세션 삭제 시 연결을 비우고 재로그인·재연결 전까지 발송 중단 |

- 자격 증명은 사용자와 1:1로 연결한다. 새 계정의 표시 이름은 초기에는 로그인 ID를 사용한다.
- 로그인 ID는 영문 소문자·숫자·밑줄 3~32자로 제한하고, 가입과 로그인에서 같은 정규화를 적용한다.
- 기존 owner의 ID, Day, 카드, 학습 세션·결과, 알림 설정은 그대로 보존한다. 기존 데이터를 새 사용자 행으로 복사하지 않는다.
- 기존 데이터가 있는 DB에서는 초기 설정 명령이 정확히 기존 owner를 확인한 뒤 자격 증명을 연결한다. 중복 연결이나 모호한 상태에서는 중단한다.
- 빈 DB에서는 초기 설정 명령으로 첫 사용자와 자격 증명을 함께 만든다.
- 가입 시 사용자·자격 증명 생성과 초대 코드 사용 처리를 한 transaction에서 수행한다. 동시 가입 두 건이 같은 코드를 소비하지 못하게 한다.
- 새 테이블의 고유 제약과 사용자·만료 시각 조회용 인덱스를 추가한다. 기존 `(user_id, day_number)` 제약과 사용자별 Day 배정 잠금을 재사용한다.
- 만료된 인증 세션·초대·요청 제한 행은 기존 worker의 주기 작업으로 정리한다.

## 4. 인증과 가입 흐름

### 사용자 흐름

1. 운영자가 서버 명령으로 초대 코드를 발급한다. 기본 유효기간은 7일이고 1회만 사용할 수 있다.
2. 사용자가 가입 화면에서 초대 코드, 아이디, 비밀번호를 입력한다.
3. 가입 성공 시 인증 세션을 새로 발급하고 빈 단어장을 연다.
4. 첫 업로드는 해당 사용자의 Day 1이 된다.
5. 이후에는 아이디·비밀번호로 로그인하고 자신의 학습을 이어간다.

### 인증 규칙

- 비밀번호는 Node.js 내장 비동기 `crypto.scrypt`와 사용자별 무작위 salt로 해시한다. 알고리즘·비용·salt를 해시와 함께 저장한다.
- 초기 비밀번호 정책은 15~128자, 공백·유니코드 허용으로 잡는다. 임의의 조합 규칙이나 자동 잘라내기는 넣지 않는다.
- scrypt 비용은 OWASP 권고 설정을 출발점으로 삼고 실제 실행 환경에서 메모리·처리 시간을 확인한다. Node.js의 기본 비용·메모리 제한을 그대로 보안 기준으로 간주하지 않는다.
- 브라우저에는 무작위 인증 토큰만 넣고 DB에는 토큰 해시만 저장한다. 인증 토큰을 localStorage에 저장하지 않는다.
- 쿠키는 기존 HttpOnly·SameSite 정책을 유지하고 운영 HTTPS에서는 Secure를 적용한다. 인증 세션 유효기간은 기존과 같은 최대 30일로 시작한다.
- 로그인·가입 시 새 세션을 발급한다. 로그아웃은 현재 인증 세션을 서버에서 무효화한다.
- 로그인 성공 시 요청 쿠키에 이전 인증 세션이 있으면 그 세션과 연결된 기기 구독도 무효화한다. 로그인 실패로 기존 로그인 상태를 변경하지 않는다.
- 비밀번호 변경·운영자 재설정은 해당 계정의 모든 인증 세션을 무효화한다. 초기에는 변경과 복구 모두 운영 명령으로 제공한다.
- 존재하지 않는 아이디와 틀린 비밀번호는 같은 로그인 실패 응답을 반환하고, 없는 계정에도 동등한 비밀번호 해시 검증 작업을 적용한다.
- 로그인·가입에는 요청 제한을 적용한다. 로그인은 계정 키와 신뢰할 수 있는 IP 경로를 함께 고려하고, 가입은 비밀번호 해시 계산 전에 초대 코드와 요청 제한을 검사한다.
- 외부에서 임의로 보낸 전달 헤더를 신뢰하지 않는다. IP 전달은 Next.js 프록시와 실제 운영 역프록시 구성을 확인해 설정한다.
- 상태 변경 API는 허용된 앱 Origin을 검사한다. Next.js API 프록시에도 Origin 전달을 추가한다. Origin이 없거나 허용되지 않은 브라우저 변경 요청은 거부한다.
- 비밀번호, 쿠키, 초대 코드, 인증 토큰을 애플리케이션 로그에 남기지 않는다.

### API와 운영 명령

| 종류 | 계획 |
| --- | --- |
| `GET /api/auth/session` | 인증 상태와 최소 사용자 정보 반환 |
| `POST /api/auth/login` | 아이디·비밀번호 검증, 새 인증 세션 발급 |
| `POST /api/auth/register` | 초대 코드 소비, 계정 생성, 새 인증 세션 발급 |
| `POST /api/auth/logout` | 현재 인증 세션과 해당 기기의 푸시 연결 해제 |
| 초기 설정 명령 | 기존 owner 연결 또는 빈 DB의 첫 계정 생성 |
| 초대 명령 | 초대 코드 생성·취소 |
| 비밀번호 재설정 명령 | 계정 비밀번호 교체와 전체 인증 세션 무효화 |

운영 명령은 기존 backend 빌드에 포함되는 작은 CLI로 제공한다. 비밀번호는 명령 인자나 로그에 넣지 않고 입력받는다. 초대 코드 원문은 발급 결과에서 운영자에게만 한 번 보여준다. 운영 명령에 대응하는 공개 관리 API는 만들지 않는다.

## 5. 계정별 데이터 접근과 기기 상태

- 백엔드가 인증 세션에서 얻은 사용자 ID만 사용한다. 요청 본문·URL의 `userId`로 소유자를 선택할 수 없게 한다.
- Day 목록·업로드, 학습 시작·조회·답변·라운드 진행·반복, 카드 조회, 알림 설정·테스트·구독 변경 모두 사용자 범위를 확인한다.
- 타인의 Day·학습 세션 ID를 넣으면 404로 응답하고 데이터나 학습 상태를 변경하지 않는다. UUID 형식 검증도 유지한다.
- 인증을 생략하는 기존 통합 테스트는 실제 테스트 계정을 생성하고 로그인하도록 바꾼다. 런타임 요청이 인증 없이 owner로 돌아가는 경로는 없앤다.
- 프론트엔드 이어하기 키는 `chanvoca:<userId>:active-session`으로 바꾸고 이전 공용 키는 제거한다.
- 로그아웃·인증 만료 시 화면의 카드·세션·Day 목록을 비운다. API의 인증 실패는 로그인 화면으로 이어지게 한다.
- 로그아웃 또는 같은 브라우저의 계정 변경 시 이전 기기 푸시 연결을 해제한다. 여러 탭의 로그인·로그아웃 변경도 전달해 이전 계정 화면을 비운다.
- 푸시 구독에는 연결한 인증 세션을 기록한다. 로그아웃·비밀번호 재설정·인증 만료 뒤에는 해당 연결에서 새 푸시 전송을 시작하지 않는다. 로그인 후 이미 알림 권한을 허용한 구독만 다시 연결하며, 최초 권한 요청은 기존처럼 사용자 버튼으로 처리한다.
- 푸시 작업에는 발급 당시 사용자 ID와 인증 세션 ID를 함께 기록하고, worker가 구독의 현재 연결과 비교한다. A → B → A로 재로그인해도 처음 A의 대기 작업은 새 연결에서 발송되지 않게 한다.
- 전환 전에 생성된 사용자 정보 없는 대기 푸시 작업은 발송 대상에서 제외한다. 다음 스케줄이나 사용자 테스트 요청으로 새 형식의 작업을 생성한다.
- 기기 알림은 인증 세션 만료 시 중단되고 재로그인·구독 재연결 후 재개된다. 이미 푸시 공급자에 전송한 알림의 취소는 보장하지 않으며, 알림 본문에는 단어·학습 결과 등 개인 내용을 넣지 않는다.
- 예문 생성은 기존 card ID 기반 큐를 유지한다. 사용자 요청에서 카드·Day의 소유권을 확인한 뒤에만 작업을 생성한다.

## 6. 증가하는 사용량에 대한 최소 대응

- 기존 파일당 10 MiB·5,000행 제한을 유지한다.
- 사용자별 일일 신규 카드 한도는 초기 제안값 5,000개로 둔다. `MAX_DAILY_CARDS` 환경변수 하나로 운영 시 조정한다.
- 일일 기준은 Asia/Seoul의 자정으로 명시한다. 업로드 transaction에서 사용자별 잠금을 잡고 그날 저장된 카드 수와 새 카드 수의 합을 검사한다.
- 한도를 넘으면 Day·카드·예문 작업을 모두 저장하지 않고 이유와 재시도 가능한 시점을 반환한다. 동시 업로드로 한도를 우회하지 못하게 한다.
- 기존 작업 큐의 동시 처리·재시도 제한은 유지한다. 카드 한도는 신규 생성량을 제한하는 장치이며, 실제 Groq 호출 수에는 기존 재시도 횟수도 반영됨을 문서화한다.
- 사용자별 업로드량과 큐 대기량을 기존 로그로 확인한다. 새로운 통계 대시보드나 Redis는 추가하지 않는다.
- 특정 사용자 수까지 수용한다고 미리 보장하지 않는다. 병목이 확인되면 worker 처리량·DB 쿼리·인덱스를 근거로 조정한다.

## 7. 단계별 상세 진행 계획

아래는 승인한 실행·검증 기준이다. 구현 후 실제 실행 결과는 MULTI_USER_VERIFICATION.md에 기록한다. 기준의 모든 조합을 전수 검증한 것으로 간주하지 않으며, 운영에 중간 단계를 배포하지 않는다.

| 단계 | 선행 조건 | 산출물 | 단계 통과 기준 |
| --- | --- | --- | --- |
| 0. 검증 준비 | 없음 | 테스트 DB 가드, 기준 fixture, 기존 동작 기준선 | G0: 실제 데이터와 분리된 검증 환경·실행 대상 확인 |

### 단계 0. 검증 환경과 기존 동작 기준선

**진행 작업**

1. 작업 시작 시 Git 상태와 변경 예정 파일을 확인한다. 기존 `.nvmrc` 삭제와 별도 계획 파일 등 사용자의 변경은 건드리지 않는다.
2. 테스트용 PostgreSQL과 `_test` 접미사의 전용 DB를 준비한다. `TEST_DATABASE_URL`에만 연결하며 실제 `backend/.env`를 테스트용으로 자동 로드하지 않는다.
3. 파괴적 정리 SQL 전에 대상이 테스트 DB인지 검사한다. 접속 문자열이 달라도 host·port·DB가 실제 앱 DB와 같으면 거부한다. 접속 정보와 비밀번호는 출력하지 않는다.
4. 기존 `node:test`·`tsx`·Fastify `app.inject()`를 재사용한다. 현재 backend의 `test` 스크립트가 파일을 직접 나열하므로 새 테스트 파일도 반드시 등록한다.
5. 현재 DB 없는 테스트의 skip 정책을 확인하고, 필수 통합 검증에서는 DB 누락·가드 실패를 명시적 실패로 처리하도록 준비한다.
6. 기존 migration 2개만 적용한 테스트 DB에 owner와 단어·진행 중/완료 학습·답변·알림 설정 fixture를 만든다. 새 migration 전후를 비교할 기준 데이터를 기록한다.
7. Groq 호출과 `web-push` 발송은 테스트 대역으로 바꾼다. 테스트에서 실제 외부 API 키나 실제 사용자 구독을 사용하지 않는다.

**테스트와 검증**

- `PRE-01`: DB 설정 없음·일반 앱 DB 이름·앱과 동일한 DB 연결은 파괴적 SQL 실행 전에 거부한다.
- `PRE-02`: 기존 lint·타입 검사·테스트·빌드 결과를 기록한다. 기존 실패는 새 변경의 실패와 구분하고 숨기지 않는다.
- `PRE-03`: 새 테스트가 실제 실행 목록에 포함되는지 확인한다. 테스트 파일만 추가하고 실행에서 빠진 상태는 실패다.

**G0 통과 기준**: 대상 DB가 검증 전용임을 확인하고 기준 fixture를 재생성할 수 있다. 기존 필수 검사 실패가 남으면 해당 영향 범위의 완료 판정을 보류한다.

### 단계 1. 인증 스키마와 운영 명령

**주 변경 대상**: `backend/db/migrations/0003_multi_user_auth.sql` 예정, `backend/src/modules/auth/`의 기존 인증 코드와 신규 CLI, `backend/package.json`.

**진행 작업**

1. 인증 테이블 4개, 제약·인덱스, 푸시 구독의 인증 세션 연결 열을 하나의 후속 migration으로 추가한다. 기존 사용자·학습 데이터는 재작성하지 않는다.
2. 인증 세션 삭제 시 푸시 구독의 연결 열은 비운다. 카드·학습 기록이 인증 세션 삭제에 따라 삭제되지 않게 한다.
3. 초기 설정 명령을 만든다. 기존 DB에서는 기존 owner에만 자격 증명을 연결하고, 빈 DB에서는 첫 사용자와 자격 증명을 함께 생성한다.
4. 재실행 시 기존 비밀번호를 덮어쓰지 않는다. owner가 없는데 다른 데이터가 있거나 이미 연결된 자격 증명이 있으면 이유를 표시하고 중단한다.
5. 초대 생성·취소 명령과 비밀번호 재설정 명령을 만든다. 원문 비밀번호는 인자로 받지 않고, 초대 코드 원문은 발급 시 한 번만 출력한다.
6. 비밀번호 재설정은 비밀번호 해시 교체·전체 인증 세션 무효화·연결된 푸시 중단을 같은 transaction에서 처리한다.
7. CLI는 TypeScript 개발 실행과 빌드된 JavaScript 실행을 모두 확인한다. 운영 이미지에는 `tsx`가 없으므로 빌드된 CLI가 실행되어야 한다.

**테스트와 검증**

- `DB-01`: 빈 DB에서 migration 성공, 재실행 시 추가 변경 없음, FK·고유 제약 동작.
- `DB-02`: 기존 owner fixture에 migration·초기 연결 후 owner ID와 기존 데이터의 행 내용이 동일함.
- `DB-03`: 초기 설정 중 오류를 발생시켰을 때 사용자·자격 증명이 일부만 남지 않음. 재실행·모호한 상태는 비정상 종료 코드와 함께 중단.
- `DB-04`: 초대 생성·취소·만료 상태가 저장되고 DB에는 원문 코드가 없음. 비밀번호 재설정 후 이전 비밀번호와 모든 이전 인증 세션을 거부.
- `DB-05`: 인증 세션 정리 후에도 사용자·Day·카드·학습 결과가 보존되고 푸시 연결만 해제됨.

**G1 통과 기준**: `DB-01~05` 통과. 신규 인증 테이블과 의도한 연결 열 외의 기존 데이터 변경 0건. 예상하지 않은 변경이 있으면 다음 단계의 전환 검증을 중단한다.

### 단계 2. 로그인·초대 가입·인증 세션

**주 변경 대상**: `backend/src/modules/auth/auth.ts`, `auth.routes.ts`, `backend/src/app.ts`, `frontend/src/app/api/[...path]/route.ts`, 인증 테스트.

**진행 작업**

1. 입력 검증과 비밀번호 해시·검증을 구현한다. 아이디는 공백 제거·소문자화 규칙을 일관되게 적용하고 비밀번호는 trim·정규화·잘라내기를 하지 않는다. 비밀번호 길이는 유니코드 코드 포인트 기준으로 계산한다.
2. 비동기 scrypt의 비용과 메모리 상한을 명시한다. 실제 scrypt 검증 테스트를 남기고, 동일 비밀번호도 salt가 달라 다른 해시를 생성하는지 확인한다.
3. 인증 쿠키 → 토큰 해시 조회 → 만료·무효화 확인 → 요청 사용자 설정 순서로 인증한다. 인증 저장소 오류를 로그인 성공이나 owner 대체로 처리하지 않는다.
4. 초대 유효성 검사, 코드 잠금·소비, 계정 생성, 인증 세션 발급을 한 transaction으로 묶는다. 중복 아이디 등으로 가입이 실패하면 초대도 미사용 상태로 남긴다.
5. 성공한 로그인에서만 이전 요청 쿠키의 인증 세션을 교체한다. 여러 기기의 로그인은 별도로 유지하되 비밀번호 재설정 시에는 모두 무효화한다.
6. 인증 공개 경로를 session·login·register·logout으로 명시한다. `/api/auth/`라는 경로 접두어만으로 향후 모든 인증 하위 API를 공개하지 않는다.
7. 로그인·가입 요청 카운터는 PostgreSQL에 저장하고 원자적으로 증가시킨다. 초기 제안값은 로그인 아이디당 15분 10회·IP당 15분 60회, 가입 IP당 1시간 10회다. 영구 계정 잠금은 넣지 않는다.
8. 허용 Origin 검사를 프록시와 백엔드에 연결한다. 신뢰할 수 없는 IP 전달 헤더로 요청 제한을 우회하지 못하게 한다.
9. 로그에 비밀번호·쿠키·토큰·초대 코드가 없는지 확인한다. 테스트는 고유한 가짜 비밀값을 넣고 출력 전체에서 누출 여부를 검사한다.

**응답 계약안**

| 상황 | 응답 및 부수 효과 |
| --- | --- |
| 로그인 성공 / 가입 성공 | 200 / 201, 새 인증 쿠키와 최소 사용자 정보 |
| 잘못된 입력 / 초대 사용 불가 | 400, 인증 세션·부분 계정 생성 없음 |
| 중복 로그인 ID | 409, 초대 코드 미소비 |
| 잘못된 비밀번호 / 존재하지 않는 ID | 같은 401 응답, 새 인증 세션 없음 |
| 인증 없는 보호 API | 401, 도메인 데이터 변경 없음 |
| 인증 없는 session 확인 | 200과 `authenticated: false`, 인증 토큰 반환 없음 |
| 허용되지 않거나 없는 Origin의 변경 요청 | 403, 코드 소비·해시 계산·데이터 변경 전에 거부 |
| 요청 제한 초과 | 429와 `Retry-After`, 영구 잠금 없음 |
| 로그아웃 반복 | 동일하게 성공 처리, 쿠키 삭제, 다른 계정·기기의 세션은 유지 |
| 인증 DB 조회 실패 | 503, 로그인 허용이나 기본 owner로 대체하지 않음 |

**테스트와 검증**

- `AUTH-01`: 아이디 2/3/32/33자, 허용하지 않은 문자, 공백·대소문자 정규화, 비밀번호 14/15/128/129자·공백·한글·이모지 경계를 검사.
- `AUTH-02`: 실제 해시 검증·다른 salt·틀린 비밀번호·깨진 저장 해시를 검사하고 원문 저장·출력이 없음을 확인.
- `AUTH-03`: 로그인 성공, 알 수 없는 ID와 틀린 비밀번호의 동일 응답, 로그인 실패 후 기존 세션 유지 확인. 응답 시간의 정확한 일치를 요구하는 불안정한 테스트는 만들지 않음.
- `AUTH-04`: 누락·변조·만료·무효화·로그아웃된 세션과 기존 공용 서명 쿠키를 거부. 쿠키의 HttpOnly·SameSite·운영 Secure 속성 확인.
- `AUTH-05`: 동일 초대 코드로 서로 다른 ID의 동시 가입 2건 실행 시 정확히 1건만 201. 실패한 요청의 사용자·자격 증명·인증 세션 추가 0건.
- `AUTH-06`: 중복 ID와 가입 중 오류에서 초대 소비·계정·인증 세션 전체 롤백. 만료·사용·취소된 코드는 400.
- `AUTH-07`: 두 API 인스턴스에서 제한 카운터 공유, 재시작 후 제한 유지, 시간 창 경계에서 재허용, 위조 전달 헤더 우회 실패 확인.
- `AUTH-08`: 올바른·외부·누락·`null` Origin을 실제 Next.js 프록시 경로로 검사. 거절 시 DB 상태와 비밀번호 해시 호출 수가 변하지 않음.
- `AUTH-09`: 로그아웃과 재설정 후 이전 쿠키를 직접 재사용해도 거부. DB 장애에서는 503이며 민감값이 응답·로그에 없음.

**G2 통과 기준**: `AUTH-01~09` 통과. 동시 초대 사용 검증은 독립 fixture로 20회 반복해 이중 가입 0건. 프록시 포함 검증은 `app.inject()`만으로 대체하지 않는다.

### 단계 3. 모든 API의 데이터 소유권 연결

**주 변경 대상**: `days.routes.ts`, `study.routes.ts`, `notifications.routes.ts`, `system/owner.ts`, 기존 업로드·학습 통합 테스트와 신규 권한 테스트.

**진행 작업**

1. `getOwnerId()`의 모든 호출자를 다시 검색하고 일반 요청의 호출을 로그인 사용자 ID로 교체한다.
2. 생성·조회·변경·작업 enqueue를 모두 확인한다. 읽기 API만 분리하고 답변 저장이나 반복 생성에서 owner가 남지 않게 한다.
3. 하위 카드·학습 시도는 소유권을 확인한 Day·학습 세션을 통해 접근한다.
   - path·body의 Day·카드·학습 세션 ID는 문자열과 UUID 형식을 확인한 뒤 SQL에 전달한다. 기존에 검증이 빠진 경로도 함께 맞춘다.
4. `userId`를 body·query에 추가해도 서버의 인증 사용자 ID를 바꾸지 못하게 한다.
5. 기존 인증 생략 fixture를 실제 로그인 fixture로 바꾸고 인증 없는 owner 대체 경로를 제거한다.
6. A·B의 서로 다른 데이터와 빈 계정 C로 아래 접근 매트릭스를 실행한다.

| 대상 | 검증 요청 | 기대 결과 |
| --- | --- | --- |
| Day 목록·업로드 | A·B가 각각 조회·업로드 | 자기 목록만 표시, 각자 Day 1 시작 |
| 학습 시작 | A가 B의 `targetDayId` 또는 `repeatOfSessionId` 사용 | 404, 학습 세션·카드 연결 생성 0건 |
| 학습 조회·라운드·답변 | A가 B의 학습 세션 ID 사용 | 404, B의 답변·통과 상태·요약값 변경 0건 |
| 카드 목록 | A의 세션+B의 Day 또는 B의 세션+A의 Day | 404, 카드 내용 반환 없음 |
| 다른 카드로 답변 | A의 정상 세션에 B의 카드 ID 사용 | 기존 카드 검증에 따른 4xx, 답변·카드 상태 변경 없음 |
| 알림 설정·테스트 | A의 쿠키에 B의 `userId`를 추가 | A만 대상으로 처리, B의 설정 변경·작업 생성 없음 |
| 푸시 구독 삭제 | A가 B의 endpoint 제출 | B의 구독 변경 없음. 기존 204 정책은 유지 가능 |
| 빈 계정 | C가 목록·학습 시작 요청 | 목록은 빈 배열, 학습 시작은 기존 빈 상태 응답 |

**테스트와 검증**

- `ISO-01`: 모든 보호 경로에서 쿠키 없음은 401. 로그인 fixture로 정상 흐름도 함께 실행.
- `ISO-02`: 위 매트릭스를 A → B, B → A 양방향으로 실행하고 응답과 DB 부수 효과를 모두 검사.
- `ISO-03`: 위조 `userId`와 카드·세션·Day 혼합 요청으로 소유권 우회가 없는지 확인. 형식이 잘못된 UUID·숫자·배열·객체 ID는 400이며 DB 형 변환 오류가 500으로 노출되지 않음.
- `ISO-04`: 두 사용자가 동시에 업로드할 때 각각 자기 Day 번호가 증가하고 카드·예문 작업 연결이 섞이지 않음.
- `ISO-05`: 기존 중복 단어, 전체 반복, 답변 재전송의 멱등성, 복습 라운드 테스트가 인증 적용 후에도 통과.

**G3 통과 기준**: `ISO-01~05` 통과. 타인 데이터 응답·변경·작업 생성이 한 건이라도 있으면 중단한다. 코드 검색에서 일반 route의 `getOwnerId()` 호출이 0건이어야 한다.

8. 이미 허용된 푸시 구독의 재연결을 단계 5와 연결한다. 지원되지 않는 브라우저에서도 로그인·학습은 정상 동작해야 한다.

**테스트와 검증**

- `UI-02`: A 로그아웃 → B 로그인 → B 새로고침에서 A의 단어·통계·세션 ID가 표시되지 않음. 변조된 이어하기 ID도 서버에서 차단.

### 단계 5. 푸시 연결·카드 한도·만료 데이터 정리

**주 변경 대상**: `notifications.routes.ts`, `notifications.worker.ts`, `days.routes.ts`, `backend/src/worker.ts`, 알림·업로드 통합 테스트.

**진행 작업**

1. 푸시 구독을 사용자와 현재 인증 세션에 연결한다. 다른 계정의 유효한 세션에 연결된 endpoint는 임의로 빼앗지 못하게 하고, 이전 연결이 무효화된 기기만 재연결한다.
2. 로그아웃·성공한 계정 전환·비밀번호 재설정 시 해당 세션 연결을 무효화한다. 구독 해제 요청이 브라우저에서 실패해도 서버의 무효화된 세션으로 발송을 계속하지 않는다.
3. 스케줄러와 테스트 알림의 payload에 사용자 ID·인증 세션 ID를 넣는다. worker는 전송 직전에 구독 연결과 세션 유효성을 확인한다.
4. 이전 형식·해제된 구독·다른 계정 또는 다른 인증 세션의 작업은 발송 없이 종료한다. 이미 외부 전송을 시작한 알림은 취소 보장 대상에서 제외한다.
5. 일일 카드 한도는 기존 사용자별 업로드 잠금 안에서 검사한다. 오늘의 저장 카드 합계와 새 카드 수가 한도를 넘으면 transaction을 종료하고 429·오류 코드·다음 한국 자정까지의 `Retry-After`를 반환한다.
6. 시간 창은 Asia/Seoul 자정 이상, 다음 자정 미만으로 고정하고 UTC로 저장된 업로드 시각에 적용한다. 실패한 업로드나 다른 사용자의 카드는 합산하지 않는다.
7. 만료 세션·초대·요청 카운터는 기존 worker에서 10분 간격, 한 번에 제한된 건수로 정리한다. 기존 예문·푸시 작업 처리를 막지 않고 정리 실패를 기록한 뒤 다음 주기에 재시도한다.
8. 잘못된 `MAX_DAILY_CARDS` 값은 기동 시 거부한다. 한도를 우회하는 기본값이나 제한 없는 동작으로 대체하지 않는다.

**테스트와 검증**

- `PUSH-01`: A·B 설정·시간대·구독에 따라 각자 작업만 생성되고 같은 날짜의 중복 실행에서도 구독별 작업이 한 건만 생성됨.
- `PUSH-02`: A 작업 생성 → 로그아웃 → B 재연결에서 A의 대기 작업 전송 0건. A → B → A에서도 최초 A의 작업 전송 0건.
- `PUSH-03`: 세션 만료·재설정·구독 해제·이전 형식 payload는 공급자 호출 0건. 정상 현재 연결만 호출 1건.
- `PUSH-04`: A가 다른 계정의 유효한 구독을 재연결하려 하면 409이며 B의 구독이 유지됨. 이전 연결이 무효화된 동일 브라우저는 재연결 가능.
- `PUSH-05`: 로그아웃 후 다른 기기의 유효한 A 세션·구독은 유지. 공급자 오류의 기존 재시도·구독 비활성화 정책은 유지.
- `QUOTA-01`: 테스트 한도 10개에서 9+1개는 성공, 10+1개는 거부. 거부 후 Day·카드·작업 수가 동일함.
- `QUOTA-02`: 같은 사용자가 각각 6개인 업로드 2건을 동시에 요청하면 한 건만 성공하고 총 6개만 저장됨. 독립 fixture로 20회 반복.
- `QUOTA-03`: A가 한도를 써도 B는 업로드 가능. 실패한 파일은 한도 미소비. 한국 시각 23:59:59와 다음 날 00:00:00 경계 확인.
- `CLEAN-01`: 만료 행만 삭제하고 활성 세션·초대·카운터는 유지. 세션 정리 후 푸시는 중단되지만 학습 데이터는 동일함.
- `CLEAN-02`: 정리 대상이 배치 크기보다 많아도 여러 주기에 걸쳐 처리되고 정리 오류 이후 예문·푸시 처리가 계속됨.

**G5 통과 기준**: `PUSH-01~05`, `QUOTA-01~03`, `CLEAN-01~02` 통과. 테스트 대역의 발송 횟수와 실제 DB 상태로 판단하며 HTTP 응답 코드만으로 완료 처리하지 않는다.

**합성 데이터 성능 확인안**

- 환경: CPU·메모리·Node·PostgreSQL 버전, 데이터 수, worker 수를 기록한다. 실제 Groq·푸시 발송 없이 대역을 사용한다.
- 데이터: 사용자 10명 × Day 30개 × 카드 50개 = 15,000개 카드. 서로 다른 학습 세션과 정상 답변 데이터를 준비한다.
- 학습 요청: 로그인 세션을 재사용하는 동시 사용자 10명이 5분간 Day 조회·학습 조회·답변 저장을 수행한다. 초기 목표는 주요 학습 API p95 500ms 이하, 예상하지 않은 5xx 0건, 데이터 혼선·중복 답변 0건이다.
- 인증: 사용자 10명당 로그인 4회씩 총 40건을 동시성 2로 실행해 측정한다. 제안한 요청 제한 안에서 초기 목표 p95 2초 이하, 서버 메모리 오류·기동 중단 0건이다. scrypt 비용을 보안 기준 아래로 낮춰 수치를 맞추지 않는다.
- 작업 큐: 예문 대역 응답 100ms 조건에서 300개 작업을 기존 단일 worker로 처리한다. 초기 목표는 5분 내 종료, 작업 유실·중복 완료 0건이며 API 응답도 함께 관찰한다.
- 이 수치는 검토용 초기 목표다. 실제 서버에서 같은 조건을 측정하기 전 특정 사용자 수를 지원한다고 확정하지 않는다. 목표를 넘으면 병목과 측정 환경을 기록하고 조정안을 검토한다.

**브라우저 확인 범위**

- 실제 사용할 Windows 브라우저에서 개발 모드와 빌드 후 실행을 확인한다.
- 모바일 화면 폭에서는 입력·오류 표시·학습·계정 전환을 확인한다. 화면 폭 에뮬레이션을 실제 모바일 PWA 확인과 혼동하지 않는다.
- HTTPS 환경의 Secure 쿠키와 실제 모바일 PWA 재로그인·알림 재연결은 환경·기기가 확보되었을 때 직접 확인한다. 미확보 항목은 미검증으로 남기며 결과를 추정하지 않는다.
- 실제 기기 푸시 수신 검증은 사용자 통제하의 테스트 계정·기기에서만 별도로 수행한다. 자동 검증에서는 공급자 호출 대역을 사용한다.

**G6 통과 기준**: G1~G5와 필수 명령 통과, 핵심 브라우저 시나리오 완료, 데이터 보존·권한·원자성 관련 미해결 오류 0건. 운영 환경·실기기에서만 가능한 항목은 별도 표기하고 해당 환경에 대한 운영 준비 완료를 선언하지 않는다.

| 알림 worker·스케줄러 | 기존 `notifications.worker.test.ts`·통합 테스트 확장 | 실제 DB, 발송 대역 호출 횟수·대상 검사 |
| 한도·동시성·정리 | 업로드 통합 테스트와 필요한 worker 정리 테스트 | 동시 요청·고정 시각·경계값·실패 주입 |
| 프록시·화면 | 기존 frontend 테스트로 가능한 범위 + 실제 브라우저 | Origin·쿠키 전달, 계정 전환·지연 응답·다중 탭 |
| 성능·복구 | 전체 검증 단계에서 별도 실행 | 합성 데이터·내장 HTTP 기능·DB 백업/복구 결과 |

파일을 늘리기 위한 테스트 분리는 하지 않는다. 신규 테스트가 필요하면 기존 테스트 파일에 자연스럽게 들어가는지 먼저 확인하고 backend의 명시적 실행 목록도 함께 갱신한다.

### 검증 데이터와 판정 방법

- 기존 데이터 보존은 행 수만 비교하지 않는다. `users`, `days`, `cards`, `study_sessions`, `study_session_cards`, `study_attempts`, `notification_settings`의 기본 키 순 정렬 결과와 주요 필드 전체를 전후 비교한다.
- `push_subscriptions`는 기존 endpoint·소유자·키가 보존되는지 확인하되, 의도한 인증 연결 해제·재연결 상태 변화는 따로 검증한다. 기존 대기 푸시를 발송하지 않는 변경도 승인 대상에 명시한다.
- 소유권 거부 검증은 응답뿐 아니라 타인 데이터, 새 학습 세션·답변·작업 수가 바뀌지 않았는지 확인한다.
- 동시성 검증은 서로 독립된 DB 연결·트랜잭션에서 요청을 겹치게 실행한다. 순차 요청 두 번으로 동시성을 검증했다고 하지 않는다.
- 시간 경계·만료 테스트는 긴 대기 대신 고정 시각과 DB 만료값을 사용한다. 실제 시간에 의존하는 불안정한 지연 테스트는 피한다.
- 실제 해시·DB transaction·프록시 전달이 필요한 검증을 모두 mock으로 대체하지 않는다. Groq·푸시 공급자처럼 외부 부수 효과가 있는 지점만 대역으로 바꾼다.

### 결과 기록과 중단 기준

각 단계의 결과는 `검증 ID / 실행 명령 또는 재현 절차 / 기대값 / 실제값 / 통과·실패·미실행 / 남은 문제`로 기록한다. 현재 실행한 범위와 미검증 항목은 MULTI_USER_VERIFICATION.md에서 구분한다.

| 상황 | 판정과 후속 조치 |
| --- | --- |
| 기존 데이터 유실·예상하지 않은 변경 | G1 실패. 원인을 수정하고 보존 검증부터 다시 실행 |
| 타인 데이터 읽기·변경·작업 생성 | G3 실패. 화면 확인보다 권한 오류 수정 우선 |
| 초대 이중 사용·카드 한도 초과 | 해당 transaction 검증 실패. 독립 연결의 동시성 재현 후 수정 |
| 무효화된 세션으로 인증·새 푸시 전송 | G2 또는 G5 실패. 무효화와 전송 대상 검증 경로 수정 |
| DB 없음·필수 테스트 skip·새 테스트 미등록 | 미검증. 통과로 집계하지 않음 |
| 외부 API 대역만 통과, 실기기 없음 | 자동 검증만 통과. 실제 수신·해당 기기 지원은 미검증 |
| 필수 검사 통과, 성능 초기 목표 초과 | 기능 검증과 성능 검증을 구분. 병목·측정값을 제시하고 운영 용량 판단 보류 |
| 계획과 다른 구현·추가 의존성 필요 | 차이와 이유를 명시하고 계획·검증 기준을 함께 갱신 |

원인 수정 뒤에는 실패한 검증과 영향받는 인접 경로부터 재실행하고, 최종 단계에서 전체 회귀 검증을 수행한다. 성공 결과를 얻기 위해 기준을 사후에 조용히 낮추지 않는다.

## 9. 운영 전환과 되돌리기

이 작업에서는 로컬 구현·테스트와 사용자 실행용 절차까지만 준비한다. 운영 배포와 운영 DB 변경은 수행하지 않는다.

### 사용자 실행용 전환 순서

운영 전에 실제 앱의 HTTPS Origin, 신뢰할 역프록시·IP 전달 경로, 서버 CPU·메모리, 확인 가능한 실제 모바일 기기를 확정한다. 이 정보가 없는 항목은 로컬 검증 결과로 대체해 운영 확인 완료로 처리하지 않는다.

| 순서 | 작업 | 다음 순서로 넘어가는 조건 |
| --- | --- | --- |
| 1 | 유지보수 시간을 확보하고 웹 접근·API 쓰기·worker를 중지 | 새 업로드·학습 답변·푸시 전송이 시작되지 않음 |
| 2 | 중지 시점의 DB 백업과 버전·환경 설정 목록 보관 | 백업 파일 생성뿐 아니라 별도 DB로 복원해 데이터 비교 성공 |
| 3 | 새 이미지·빌드에서 migration 실행 | migration 성공, 기존 사용자·학습 데이터 비교 일치 |
| 4 | 초기 설정 CLI로 본인 계정에 기존 owner 연결 | 동일 owner ID 유지, 초기 설정 재실행이 덮어쓰지 않음 |
| 5 | 새 API·worker·frontend를 같은 버전으로 실행 | health·ready 정상, 미인증 데이터 요청은 401, 기존 쿠키 거부 |
| 6 | 본인 계정의 실제 사용자 흐름 확인 | 기존 Day·이어하기·결과·알림 설정 확인, 현재 기기 구독 재연결 |
| 7 | 친구 초대와 별도 계정 첫 사용 확인 후 접근 재개 | 새 계정의 빈 단어장·Day 1 확인, 계정 간 접근 차단 확인 |

전환 과정에서는 기존 로그인 쿠키가 무효화되어 모든 기기에서 다시 로그인해야 한다. 이전 푸시 구독 행·알림 설정은 보존하되 현재 인증 세션에 재연결되기 전까지 해당 기기 발송은 중단한다. 재로그인 뒤 기존에 허용한 구독만 자동으로 재연결하고 권한이 없는 기기는 별도 버튼으로 허용받는다.

### 복구 연습과 승인 기준

- `OPS-01`: 전환 전 fixture의 백업을 별도 테스트 DB에 복원한 뒤 owner ID·Day·카드·학습 기록·설정이 일치하는지 확인한다. 단순히 백업 파일이 존재하는 것만으로 성공 처리하지 않는다.
- `OPS-02`: 복원 DB에서 migration → 초기 연결 → 빌드된 앱·CLI → 로그인·학습 흐름을 순서대로 재현한다. 기존 공용 쿠키는 무효이고 신규 인증만 동작해야 한다.
- `OPS-03`: `APP_ORIGIN` 누락·잘못된 일일 한도·DB 연결 실패·migration 실패에서 조용히 인증 없는 앱이 실행되지 않는지 확인한다. health 공개 여부와 데이터 접근 허용 여부를 구분한다.
- `OPS-04`: 전환 실패 후 접근·worker를 중지하고 전환 전 백업을 다시 복원하는 절차를 테스트 DB에서 연습한다. 복구 대상·소요 시간·복구 후 비교 결과를 기록한다.
- G6 자료에는 `OPS-01~04` 결과도 포함한다. 실제 운영 서버의 복구 실행을 대신 수행한 것으로 보고하지 않는다.

처음에는 테이블 추가 중심으로 변경하되, 새 계정 데이터가 생긴 후 구버전의 공용 owner 로그인으로 바로 돌아가지 않는다. 문제가 생기면 접근을 차단한 상태에서 수정하거나, 전환 전 백업을 복구한다. 백업 복구는 전환 이후 생성된 데이터를 잃을 수 있음을 명시한다.
