# 다중 사용자 전환 구현·검증 결과

- 기준일: 2026-10-27 (Asia/Seoul)
- 범위: 로컬 코드 구현과 테스트 전용 데이터 검증. 운영 배포·운영 DB migration·실제 사용자 계정 생성은 수행하지 않았다.
- 상태: 핵심 구현과 로컬 검증 완료. 운영 HTTPS·실제 모바일 기기·실제 푸시 수신은 별도 확인 필요.

## 구현 내용

- 기존 owner ID에 로그인 정보를 연결하는 초기 설정 CLI와 후속 migration을 추가했다.
- 아이디·비밀번호 로그인, 7일 일회용 초대 가입, 서버 인증 세션, 현재 세션 로그아웃을 구현했다.
- 비밀번호는 사용자별 salt를 가진 scrypt로 저장하고, 인증 토큰·초대 코드는 해시만 저장한다. 동시에 실행되는 해시 계산을 제한한다.
- 비밀번호 재설정 CLI는 해당 사용자의 모든 인증 세션을 무효화한다.
- 단어·Day·학습·답변·라운드·알림의 사용자 ID를 인증 세션에서 얻는다. 일반 API의 owner 자동 생성·대체 경로를 제거했다.
- 사용자별 이어하기 키, 현재 계정 표시, 여러 탭의 계정 변경·로그아웃 반영, 이전 계정의 지연 응답 차단을 구현했다.
- 여러 탭이 같은 학습을 진행해 라운드 충돌이 생기면 최신 서버 상태를 다시 읽는다. 답변 중복 저장은 세션 행 잠금으로 방지한다.
- 푸시 구독과 작업을 사용자·인증 세션에 연결했다. 이전 계정·이전 로그인·해제된 연결의 작업은 발송하지 않는다.
- 임의 주소로 서버 요청을 보내지 않도록 푸시 공급자 HTTPS 호스트를 저장 시와 발송 시 확인한다.
- DB 기반 로그인·가입 요청 제한, 사용자별 한국 날짜 기준 일일 신규 카드 한도, 만료 인증 데이터 정리를 구현했다.
- 앱 Origin·ID·입력 검증과 내부 오류 응답 정리를 적용하고, 기존 테스트를 실제 인증 fixture로 변경했다.
- 실제 앱 DB와 혼동할 수 있는 테스트 DB 주소·URL 재정의·루프백 별칭을 검증 전에 거부한다.

### 실제 PostgreSQL 통합 검증

- 기존 migration만 적용한 DB에 사용자·Day·카드·학습 세션·카드 연결·답변·알림 설정을 넣고 후속 migration과 초기 계정 연결 전후의 행 내용을 비교했다. 기존 owner ID와 데이터가 동일했다.
- migration 재실행과 초기 설정 중복 실행을 검증했다. 기존 연결을 덮어쓰지 않았다.
- A와 B 계정이 서로의 Day·학습 세션·카드를 조회하거나 답변·반복·라운드 작업을 수행하지 못함을 확인했다. 응답뿐 아니라 DB의 답변·세션 수를 비교했다.
- 동일 답변의 동시 재전송은 한 번만 저장되고 통계가 중복 증가하지 않았다.
- 동일 초대 코드에 대한 동시 가입을 독립 fixture로 20회 실행했다. 매번 한 계정만 생성됐다.
- 중복 ID 가입 실패 시 초대를 소비하지 않았고, 만료·취소된 초대는 거부했다.
- 로그인 실패, 알 수 없는 계정, 변조·만료·로그아웃된 쿠키, 공용 서명 쿠키를 검증했다.
- 실제 CLI로 비밀번호를 재설정한 뒤 이전 비밀번호·기존 쿠키를 거부하고 새 비밀번호로 로그인했다. 카드 데이터는 보존됐다.
- A → B → A 기기 구독 전환에서도 최초 A의 대기 작업이 발송되지 않았다. 다른 계정의 유효한 구독은 임의로 재연결할 수 없었다.
- 한도 10개에서 6개 업로드 두 건을 동시에 요청하는 검증을 20회 반복했다. 매번 한 건만 저장됐고 거절된 요청의 카드·작업은 생성되지 않았다.
- 다른 사용자의 한도 독립성, 한도 경계, 공유 요청 카운터, 위조 IP 전달 헤더, 만료 데이터의 배치 정리를 확인했다.
- 기존 중복 단어·헤더 없는 파일·학습 라운드·예문 파서·푸시 스케줄·로그 비밀값 배제 검증을 유지했다.

### 전체 HTTP 경로

빌드한 Next.js(3345) → API 프록시 → Fastify(4485) → 전용 UI 테스트 DB 경로에서 다음을 확인했다.

- 정상 Origin 전달과 외부·누락 Origin 차단.
- 차단된 가입 요청은 초대를 소비하지 않음.
- 인증 쿠키·세션 사용자 정보 전달과 no-store 응답.
- 이전 계정 헤더가 붙은 요청 차단.
- 새 계정의 빈 단어장과 기존 계정의 Day 보존.
- 로그아웃 후 기존 쿠키 재사용 차단.

## 브라우저 확인

ChatGPT in-app browser에서 테스트 데이터만 사용했다.

1. 본인 테스트 계정 로그인 후 본인 전용 단어와 Day 표시.
2. 로그아웃하면 학습 화면이 사라지고 로그인 화면 표시.
3. 초대 가입 후 별도 계정이 빈 단어장으로 시작.
4. 한 탭에서 로그아웃하면 다른 탭도 기존 학습 화면 정리.
5. 다른 탭에서 계정을 전환하면 서버의 현재 사용자로 변경.
6. 같은 계정의 두 탭이 동시에 시간 초과·라운드 진행을 해도 오류 화면에 머물지 않고 최신 라운드로 동기화.
7. 최종 가입 화면의 입력 항목·label·오류 안내 구조 확인.

이 과정에서 확인한 기존 라운드 충돌 화면은 최신 서버 상태를 다시 읽는 처리로 보완하고 두 탭에서 재검증했다. 실제 모바일 기기의 화면·키보드·PWA 동작을 대신 검증한 것으로 보지는 않는다.

## 백업·복원

- UI 테스트 API 쓰기를 중지한 뒤 pg_dump 18.6으로 테스트 DB를 백업했다.
- 새 테스트 DB에 pg_restore로 복원했다.
- public의 14개 테이블에 대해 정렬한 전체 행 내용을 비교해 모두 일치했다. 행 수만 비교하지 않았다.
- 복원 DB에서 migration 재실행, 기존 계정 로그인, 기존 Day 조회가 성공했다.
- 운영 DB의 백업·복원을 수행한 것은 아니다. 전환 이후의 새 데이터를 전환 전 백업으로 되돌리면 그 이후 데이터는 잃을 수 있다.

## 운영 적용 전 남은 확인

- 실제 HTTPS APP_ORIGIN 설정과 Secure 쿠키의 브라우저 동작.
- 실제 ingress의 전달 헤더 정제·IP 신뢰 경로. 현재는 임의의 전달 헤더를 신뢰하지 않아 프록시 주소의 요청 제한이 사용자 사이에 공유된다.
- 실제 모바일 화면·키보드·PWA 설치·알림 권한·푸시 수신·재로그인 후 재연결.
- 실제 Groq와 푸시 공급자의 운영 연결 및 용량. 자동 검증에서는 외부 발송을 하지 않았다.
- 계획서의 모든 장애 주입·UI 경계 조합을 전수 검증한 것은 아니다. 특히 정리 작업 장애 중 worker 진행, 실제 프로세스 재시작·호스트 장애 및 한국 자정의 실시간 전환은 추가 운영 환경 확인 대상으로 남긴다.

## 사용자 실행 순서

기존 데이터를 백업·복원 확인하고 유지보수 시간에 migration을 적용한다. APP_ORIGIN을 실제 HTTPS Origin으로 설정한 뒤 기존 owner에 본인 계정을 연결하고 초대를 발급한다. 비밀번호를 채팅이나 명령 인자에 넣을 필요는 없다.

```powershell
npm --workspace backend run migrate
npm --workspace backend run auth -- setup my_login
npm --workspace backend run auth -- invite
```

운영 컨테이너에서는 빌드된 CLI인 `node dist/modules/auth/auth.cli.js`를 사용한다. 세부 설정과 복구 절차는 README와 MULTI_USER_PLAN.md의 9절을 따른다.

기존 공용 비밀번호와 서명 비밀값은 더 이상 사용하지 않는다. 운영 전환 시 모든 기기에서 다시 로그인해야 하며 푸시 연결도 현재 로그인에 다시 연결되어야 한다.
